## 3. 性能实测

数据集：5 名演示学生 / 8 个活动 / 19 条报名 / 1734 条日志（小数据量，数值反映**本机基线**而非容量上限）。

| 接口 | avg | p95 | 响应体 |
|---|---:|---:|---:|
| `/api/health` | 14.0 ms | 15.1 ms | 115 B |
| `/api/activity/list` | 15.4 ms | 17.6 ms | 3.5 KB |
| `/api/signup/list` | 15.2 ms | 16.9 ms | 3.5 KB |
| `/api/hours/report` | 15.7 ms | 17.1 ms | 2.9 KB |
| `/api/report/anomaly` | 14.3 ms | 15.2 ms | 174 B |
| `/api/logs` | 12.5 ms | 12.9 ms | 3.1 KB |

并发：

- 100 并发 `activity/list`：全部成功，总耗时 **60 ms**；
- 20 并发 `hours/report`：全部成功，总耗时 16 ms；
- 服务端工作集：14.8 MB → 19.9 MB（100 并发后，未回收部分为连接/缓冲，无持续增长）；
- 容量竞态：capacity=1 两人同时报名 → `codes=0,403`，`taken=1`，无超员。

结论：小数据量下所有接口在 20 ms 量级，瓶颈尚未出现；按当前实现，**数据量增长后**的风险点是报表全量返回、异常检测全表扫描与 `size=0` 全量拉取（见缺陷 D4/D9/D11）。

## 4. 缺陷清单与处理

### 4.1 严重

无。未发现鉴权绕过、越权写入、数据丢失、基数漂移或可远程触发的崩溃。

### 4.2 一般（已在本轮修复并回归）

| ID | 问题 | 证据（修复前） | 影响 | 修复方案 | 状态 |
|---|---|---|---|---|---|
| D1 | 按字节截断切断 UTF-8 多字节字符 | 提交 600 个汉字的申诉理由 → `code=500, msg=Incorrect string value: '\xE9\x95' for column 'reason'` | 中文长文本直接失败；活动标题/内容/备注等 12 处同源 | 新增 `utf8Truncate()`：截断后回退到字符边界；12 处 `substr` 全部替换 | 已修复，600 汉字提交成功、入库 ≤500 字节 |
| D2 | 数据库错误原文回传客户端 | 同上响应含列名 `reason`、`at row 1` | 泄露表/列结构，便于构造注入探测 | `jsonErr` 统一识别 DB 错误：原文写 stderr，客户端仅收「服务器内部错误, 请稍后重试」 | 已修复，错误响应不再含 SQL |
| D3 | 申诉调整学时传负数被静默忽略 | `hours=-2` → `code=0`（被当作"未提供"，沿用原学时） | 管理员以为改成了 0/未改，结果不可预期 | 用字段存在性判断（`body.get("hours")`），负数/越界一律 400 | 已修复，`hours=-2` → 400 |
| D4 | `size=0` 返回全量 | `/api/signup/list?size=0` 返回 19 条且无 LIMIT | 数据量大时单请求拉全表，内存/带宽放大，可被用作轻量 DoS | 建议：`size=0` 归一到默认 20，硬上限 200（或显式 `all=1` 仅管理员） | **待修（P1）** |

### 4.3 建议（不影响当前演示，按优先级排）

| ID | 问题 | 风险 | 建议 | 优先级 |
|---|---|---|---|---|
| D5 | 状态码语义不统一：重复审核 400、名额满 403、未知路由 HTTP 404 而业务错误 HTTP 200 | 客户端需按字符串/特例判断，易误处理 | 统一为 409（状态冲突）/403（权限）/404（资源）；未知路由保持 HTTP 404，业务错误统一 200 并在文档写明 | P1 |
| D6 | 仅 HTTP，Token 明文存 `Preferences`，Bearer 头可被同网段嗅探 | 内网演示可接受，公网不可用 | 生产部署加 TLS（nginx 反代）+ 客户端安全存储；Token 缩短有效期并支持刷新 | P2 |
| D7 | 读接口无全局限流（仅登录/注销按账号+IP 节流） | 高频拉取报表/日志会放大 DB 压力 | 令牌桶（按 IP+角色）或反向代理限流；报表接口加短 TTL 缓存 | P1 |
| D8 | `request_log` 仅在启动时裁剪（7 天/2 万条） | 长期不重启会持续增长 | 后台线程每日裁剪一次，或写入每 N 条触发一次 | P1 |
| D9 | 异常检测 `burst` 对 `checked_at` 无索引 | 数据量大时全表扫描 | `signup(checkin, checked_at)` 复合索引；或定时汇总到统计表 | P1 |
| D10 | 一连接一线程（上限 256） | 高并发上下文切换/栈内存开销 | 当前 100 并发 60ms、内存 +5MB，规模内可接受；远期换线程池/事件驱动 | P2 |
| D11 | 报表一次返回全部学生+明细，无分页 | 响应随人数线性增长 | 排行分页 + 明细按需加载；或导出走流式 | P2 |
| D12 | App 仅构建验证，未在模拟器/真机跑 UI 用例 | UI 交互缺陷可能漏检 | 补 DevEco 模拟器冒烟：登录→报名→签到→申诉→导出 | P1 |

## 5. 改进优先级

**P0（已完成，本轮）**：D1 UTF-8 截断、D2 错误信息泄露、D3 负数静默通过 —— 均已修复并用 103 项断言 + 45 项功能回归验证。

**P1（v4.1，建议 1~2 天）**：D4 分页上限、D5 状态码统一、D7 读接口限流、D8 日志定期裁剪、D9 签到时间索引、D12 模拟器 UI 冒烟。前五项都是小改动、低风险；D5 需同步 App 的少数字符串判断。

**P2（v5，按需）**：D6 TLS/安全存储、D10 线程模型、D11 报表分页。属于规模化/生产化改造，不影响课程演示与答辩。

## 6. 结论

- 功能、边界、安全、性能、一致性、兼容性六个维度 **103/103 通过**，`verify_v4.ps1` 45/45 回归通过，App 构建 0 error；

- 当前版本可稳定用于课程演示与答辩；上生产前需完成 P1 的限流、分页、日志治理与 TLS。
