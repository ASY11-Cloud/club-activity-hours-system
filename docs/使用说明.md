# 社团活动报名与学时认定系统 使用说明

题号 86 · HarmonyOS 课程设计（SQLite 本地库 + 服务端 MySQL）· 文档对应版本 **v4.0**（服务端 `/api/health` version 4.0）

> 完整 Word 版使用说明见仓库根目录：`使用说明文档.docx`（随项目本地交付）。本 Markdown 为同源可读版本，两者内容一致。

## 1 系统概述

### 1.1 功能简介

本系统面向高校社团的活动组织与学时认定管理，提供"活动发布—报名—审核—学时认定—统计报表"的完整闭环，并支持 RFID 刷卡签到作为嵌入式扩展项。主要功能如下：

- 注册与审批：成员自助注册（学号 + 姓名 + 班级 + 登录密码，RFID 卡号可选），管理员在审核中心"注册申请"页签同意或拒绝（同意时可补绑卡号）；
- 活动发布：管理员创建活动（名称、内容、地点、时间、学时、人数上限），支持本地草稿保存与一键同步发布到服务器；
- 活动报名：普通成员浏览活动并报名，报名记录同时写入本地 SQLite 与服务器 MySQL，重复报名自动幂等去重；
- 审核认定：管理员在审核中心对报名记录"通过/驳回"，通过后服务器自动累计学时到学时汇总表；
- 用户管理：管理员查看全系统学生信息，按注册状态与学时达标情况分组，支持按学号 / 姓名 / 班级搜索；
- 账号注销：成员可在设置页自助注销本人账号（**需输入本人登录密码确认**，学号是公开信息不能作为凭据），管理员可在用户管理页注销任意学生；注销为事务级联删除（报名、学时、登录态一并清除）；
- 学时报表：提供成员排行与认定明细，本地 SQLite 统计与服务器 MySQL 统计双端对比；含达标率环形图与七大类分布条形图，并可导出 CSV；
- 学分预警：列出未达标学生（学号 / 姓名 / 班级 / 已认定 / 缺口），按缺口降序，支持一键导出；
- 活动分类与学时规则：七大类归档，支持"单活动上限"与"类别累计上限"，审核通过时按规则裁剪学时；
- 现场签到：管理员出示 60 秒轮换签到码，成员输码签到、签退，按实际在场时长折算学时（与 RFID 刷卡并存）；
- 学时申诉：成员对已通过记录发起申诉，管理员复核并可调整认定学时，全程留痕（v4.0）；
- 规则可视化：管理员在设置页直接配置七大类"单活动上限/类别累计上限"，保存即生效（v4.0）；
- 异常检测：批量签到、签到后长期未签退、认定学时超活动学时三类风险只读清单（v4.0）；
- 服务器实时日志：每次请求实时记录（内存日志 + MySQL request_log 双写），管理员可在线查看；
- 深色模式：全应用颜色走设计 token，跟随系统深浅色自动切换；
- 失败反馈：所有写操作失败都会给出明确中文原因（弹窗 toast + 页面红字），不存在"点了没反应"的静默失败；
- 嵌入式扩展：ESP32 + RFID 读卡器实机刷卡签到，到场即认定学时（扩展项）。

### 1.2 系统架构

系统采用"鸿蒙 App + 本地 SQLite + 自主 C++ Web 服务器 + MySQL"的双通道架构：App 端使用 HarmonyOS 关系型数据库（relationalStore）本地落库，保证离线可查；同时通过 HTTP 接口与自主编写的 C++ Web 服务器（监听 0.0.0.0:8000）同步数据，服务器以 MySQL 8.0 作为服务端持久化存储。数据一致性通过"本地唯一 client_id 幂等 + 服务端唯一键（uk_client、uk_act_stu）去重 + 事务化容量/学时累计"三层机制保证。

### 1.3 权限体系

系统明确区分三类角色，权限由服务端按登录 Token 统一校验，App 端同时做页面级守卫：

| 角色 | 登录方式 | 功能范围 |
|---|---|---|
| 平台管理员 | 账号 + 密码（admin_user 表） | 跨社团：**社团注册审核与停用/恢复（v5.0 重构，不再发布活动）**、审核学生注册与报名申请（通过自动累计学时）、用户管理（含注销学生）、查看服务器实时日志、全量学时报表与达标线设置 |
| 社团管理员 | 社团账号 + 密码（club 表，v5.0 重构：注册制） | **仅本社团**：社团主页与换届、**入社/退社申请审批**、成员管理、**发布/编辑/上下线本社团活动**、审核本社团活动报名、通知公告、本社团学时报表与统计 |
| 普通成员 | 学号 + 密码（student 表，密码迭代加盐存储） | 浏览可见活动（全校开放 + 本人**在册**社团的内部活动）、**社团广场浏览/搜索/申请加入/申请退出**、报名/撤销、查看我的报名与本人学时明细、查看学时排行、修改本人登录密码、注销本人账号 |

> v5.0（重构）起**社团像成员一样注册**：注册（自设账号/社团名/密码）→ 平台管理员审核 → 获得独立编号，审核通过前不能登录。学生可同时加入多个社团，加入与退出均需**社团账号审批**（审批时显示申请人已加入的社团供参考）。服务端内部用 `role + club_id` 区分「平台管理员（`club_id=0`）」与「社团管理员（`club_id>0`）」，`/api/login` 对外仍下发 `role="admin"`（兼容既有脚本与 App 的 `isAdmin` 判断），新语义通过 `club_id` / `club_name` / `account_type` 三个字段暴露。**活动发布/编辑/上下线已收敛为社团账号专属**，平台管理员调用返回 403。

## 3 快速启动

### 3.1 初始化数据库

在 MySQL 中执行建库脚本，脚本会自动创建 club_system 库及全部表，并写入演示数据：

```
mysql -u root -p123456 --default-character-set=utf8mb4 -e "source C:/Users/34520/Desktop/chapter03/server/init_db.sql"
```

### 3.2 编译并启动服务端

编译命令（Windows）：直接双击运行 `server\build.bat`，脚本会按顺序尝试 Dev-C++ 自带 MinGW64（TDM）、Dev-C++（Program Files）与 PATH 中的 g++，取首个编译成功的工具链，统一使用 `-std=c++14`。

若手工编译，等价命令为：

```
g++ -std=c++14 -O2 -Wall server.cpp -o server.exe -I "C:\Program Files\MySQL\MySQL Server 8.0\include" -L "C:\Program Files\MySQL\MySQL Server 8.0\lib" -lmysql -lws2_32
```

> 注意：部分 MinGW 为 win32 线程模型，缺少 `std::thread` / `std::mutex` 实现，编译会报 `'thread' is not a member of 'std'`；此时请使用 Dev-C++ 自带的 TDM g++（脚本已自动优先选用）。编译前需先关闭正在运行的 `server.exe`，否则文件被占用会导致链接失败。

编译成功后运行 server.exe，服务器监听 0.0.0.0:8000。验证：浏览器访问 http://127.0.0.1:8000/api/health 应返回 {"code":0,...}，其中 `db:true` 表示 MySQL 连接正常、`version` 为服务端版本（当前 5.0）。

> 老库升级无需手工改表：`dbEnsureSchema()` 在启动时做幂等迁移（新增 `club` / `club_member` / `club_leader_history` / `announcement` / `announcement_read` 表，`activity` 增 `club_id` 与 `join_scope`，`signup` 增 `club_id`），缺列会先经 `information_schema` 校验再 ALTER；迁移失败会向 stderr 打印带业务后果的告警，不会静默跳过。

**日常启动推荐双击 `server\start_server.bat`**：脚本已写死 `cd /d "%~dp0"`（避免当前目录不是 server 导致找不到 libmysql.dll），启动前先探测 3306 端口确认 MySQL 已运行，再以 `server.exe 8000` 启动。参数与手工命令行完全一致（端口 8000、MySQL 127.0.0.1:3306、root）。**这个窗口需要一直开着**，关窗口或 Ctrl+C 即停止服务；需要强制停止时双击 `server\stop_server.bat`（等价于 `taskkill /F /IM server.exe`，用于释放 8000 端口或解除 exe 文件占用以便重新编译）。

> 注意：服务端登录 Token 保存在内存中，**每次重启都会清空**，App 端会收到"登录已失效"并自动清除本地登录态，重新登录即可（不是故障）。因此演示过程中不要重启服务端。

### 3.3 构建并安装鸿蒙 App

在工程目录（chapter03\chapter03）执行：

```
hvigorw assembleHap --mode module -p product=default --no-daemon
```

产物位于 entry\build\default\outputs\default\entry-default-unsigned.hap，使用 hdc 安装到模拟器：

```
hdc install -r entry-default-unsigned.hap
```

> **真机安装需先签名**：当前构建为 unsigned HAP，可直接装入模拟器；装真机需在 DevEco Studio 的 `File → Project Structure → Signing Configs` 勾选自动签名（登录华为开发者账号后由 IDE 生成调试证书），重新 `assembleHap` 后再 `hdc install`。若验收使用模拟器演示，可跳过此步。

### 3.4 启动与登录

在模拟器打开 App，默认服务器地址为 10.0.2.2:8000（模拟器访问宿主机的标准地址），无需修改即可联调。使用演示账号登录后按角色进入对应功能。

## 5 功能与操作说明

### 5.1 登录

冷启动进入**引导页**：顶部显示服务器在线状态（可点"点此重试"），下方是"登录 / 注册 / 设置"三个入口，底部为"登录"按钮。登录页顶部可切换"普通成员 / 管理员"两种身份，普通成员填写学号与登录密码（初始密码统一为 123456，登录后可在"我的 → 设置"里修改），管理员填写账号与密码，提交后由服务端校验并签发 Token，后续请求自动携带。登录成功后**清空返回栈**进入主界面（返回键不会退回登录页），功能入口按角色显示。登录卡片下方提供"还没有账号? 去注册"与"服务器设置"两个快捷入口，未注册或连不上服务器时无需退回引导页。

### 5.2 引导页与主界面

**引导页（冷启动第一屏）**：显示服务器在线状态（可点"点此重试"）与"登录 / 注册 / 设置"三个入口。设置入口恒在，未登录也能直接改服务器地址。已登录时顶部出现用户卡片（姓名 + 角色）与"进入主界面"按钮，底部主按钮同步变为"进入主界面 ›"。

**主界面（底部 TabBar）**：

| Tab | 可见角色 | 内容 |
|---|---|---|
| 活动 | 全部 | 活动广场（分页列表 + 下拉刷新 + 触底加载）；v5.0 起只展示本人有权查看的活动，内部活动带「仅本社团」标签 |
| 管理 | 仅管理员 | 社团账号：社团主页、通知公告、**入社/退社审批**、审核中心、用户管理、发布活动、学时报表、服务器实时日志；平台管理员：**社团审核（替代发布活动）**、审核中心、用户管理、学时报表、服务器实时日志 |
| 我的 | 全部 | 成员：我的报名 / 学时报表 / **社团广场** / 通知公告 / 设置 / 系统介绍；管理员：学时报表 / 通知公告 / 设置 / 系统介绍；底部"退出登录" |

底部导航为自绘（不使用系统 Tabs），切换不销毁页面状态（分页与滚动位置保留）。**"管理" Tab 上带角标**：平台管理员 = 待审报名 + 待批注册 + **待审社团**；社团账号 = **待审入社/退社申请**——不必点进去才知道有活；顶部同时显示"有 N 条待办"直达卡片。切到"管理"时会重新拉一次待办，角标保持新鲜。

"系统介绍"进入引导页查看服务器状态、角色功能一览与验收流程，点"进入主界面"即可返回（不会在主界面栈里叠加重复页面）。管理员在"我的"页不显示"我的报名"（管理员无报名记录，报名审核在审核中心）。

### 5.3 活动广场与报名

活动广场是主界面第一个 Tab（不再有独立页面），从服务器分页拉取已发布活动（每页 10 条，滚动到底自动加载下一页，支持下拉刷新），顶部显示"共 N 个"，底部显示"上拉加载更多 / 已全部加载 (M 个)"，展示名称、时间、地点、报名人数与剩余名额。点击活动进入详情页：普通成员可点击"立即报名"，报名记录先写入本地 SQLite（离线可查），再同步服务器等待审核；若已报名则显示报名状态（待审核/已通过/已驳回）。重复点击不会产生重复记录（本地与服务器双重幂等）。

活动按**七大类**归档（思想成长 / 实践实习 / 志愿公益 / 创新创业 / 文体活动 / 社会工作 / 技能特长），广场顶部提供"全部 + 七类"横向筛选标签，活动卡片左上角显示类别徽标，右侧显示"已报 N / 上限 M"（已报人数取服务端 `taken` 计数，与名额判定同源）。

交互细节：
- **名额校验**：活动设置了人数上限且已报满时，报名按钮自动替换为"名额已满"提示，不可报名；容量统计在服务端事务内完成（先锁活动行再计数），并发报名不会超员；已驳回的报名不计入名额；**剩余名额由服务端计算后随列表下发**，App 与服务端判定口径完全一致；
- **结束时间校验**：活动结束时间已过时，详情页显示"活动已结束"并禁用报名（服务端同样拒绝，避免对历史活动补报名）；
- **时间冲突校验**：同一成员不能同时报名两个时间重叠的活动。第二个报名会被服务端拒绝并提示"与「XX 活动」时间冲突，请先撤销原报名"——这是"学时不被双算"的第一道闸门；活动未填时间（老数据）时跳过校验，不影响正常使用；
- **驳回后可重新报名**：报名被管理员驳回后，详情页按钮变为"重新报名"，点击后服务器将原驳回记录重置为待审核，无需重新填写任何信息；
- 管理员进入详情页不显示报名按钮，额外提供"下线该活动"（软删除：活动不再出现在广场，历史报名与学时记录保留）；活动处于已下线状态时该按钮变为"恢复上线"，可原地恢复；
- **状态以服务器为准**：详情页每次进入都会向服务器确认本人的报名状态并回写本地，管理员审核通过/驳回后无需先到"我的报名"点同步，回来即是审核结果（本地 SQLite 与服务器保持一致）；
- 所有二级页面（详情、我的报名、审核中心、学时报表、日志、设置、发布）左上角均有"‹ 返回"，不依赖系统返回手势。

### 5.4 我的报名

展示当前成员的全部本地报名记录与状态。进入页面会自动补传未同步记录并静默拉取一次服务器审核状态，服务器存在而本地缺失的记录（如另一台设备报名或 RFID 刷卡自动创建）会自动补全到本地，保证双端一致；也可手动点"同步服务器状态"。已刷卡签到的记录会显示"已刷卡签到"标记（来自服务端 `checkin` 字段，同步后落本地库，离线也能看到）；"报名时间"取服务器记录的时间，与本机同步时刻无关。

两条与"离线可用"配套的能力：

- **未同步补传**：报名时若服务器不可达，记录会先落在本地 SQLite 并标记"仅本地(未同步)"，页面顶部出现"有 N 条报名仅存本地"提示与"立即补传"按钮；进入页面时也会自动尝试补传。服务端按 `client_id` 幂等，反复补传不会产生重复报名；
- **撤销报名**：仅"待审核"记录显示"撤销报名"按钮，确认后同时删除服务器与本地记录并释放名额；已通过（已认定学时）与已驳回记录不提供撤销，保证学时账目不可被成员单方面改动。

### 5.5 学时报表

页面顶部为"本地 SQLite 统计"与"我的服务器学时"双端对比卡片（管理员视角右侧卡片显示"服务器全量学时"合计）；下方提供"学时排行 / 认定明细"两个页签。普通成员仅看到本人明细，管理员可查看全量排行与明细。服务器学时由审核通过自动累计（hours_total 表）。

两张卡片下方是**双端一致判定**：相同时显示绿色"✔ 双端一致"，不同则显示"⚠ 本地缓存与服务器差 X 学时"并给出"校准本地缓存"按钮。校准时以服务器报名记录为准回填本地 SQLite（含审核状态、学时、刷卡标记），之后本地统计即与服务器一致——这是验收"学时累计双端一致"最直接的演示入口。

管理员可设置**学时达标线**（页面"达标线"输入框 + 保存，写入服务端 `sys_config.required_hours`，0 表示不设线）：设置后排行行显示"达标"标签，未达标显示"距达标 X 学时"，卡片显示"达标 M/N 人"，成员端显示本人"已达标 / 未达标(差 X)"。

报表支持**导出 CSV**：按当前页签（学时排行 / 认定明细 / 预警名单）弹出系统"保存到文件"选择器，用户自选目录与文件名后直接落盘（带 UTF-8 BOM，Excel/WPS 打开不乱码）；若用户取消或系统不允许写入，则自动回退为"复制内容到剪贴板 + 展示应用沙箱路径"，两种方式都不会丢数据。

#### 5.5.1 达标率与分类分布

报表顶部新增两块可视化（纯 ArkUI 布局实现，无第三方图表库）：

- **达标率环形图**：用 `Progress(Ring)` 显示"已达标 M / 总人数 N"，环中心大字为百分比；未设置达标线时显示"未设置"，环形为灰色空环；
- **分类分布条形图**：按七大类汇总已认定学时，每行一条横向百分比条 + "学时 / 占比"，颜色随主题变化（深色模式下自动适配）。

#### 5.5.2 学分预警名单

管理员在报表页切到"预警"页签可看到**未达标学生清单**（数据来自 `/api/report/warning`）：学号、姓名、班级、已认定学时、已认定活动数、缺口学时、最近一次认定时间，按缺口从大到小排序，顶部显示"共 N 人未达标"。名单可一键导出 CSV，直接用于发通知或当面谈话。

管理员额外提供"重算学时"：以 `signup` 表中已通过的记录为唯一事实来源重建 `hours_total`，用于修复历史手工改库、异常中断造成的数据漂移；重算为事务操作，正常数据下结果与重算前一致。

### 5.6 发布活动

发布活动为管理员功能，包含"活动表单 + 本地草稿箱"两部分：

- 表单字段：活动名称（必填）、内容（多行文本）、地点、**活动类别（七大类单选）**、学时、人数上限（0 表示不限）、发布人；
- 时间选择：点击"开始时间 / 结束时间"卡片弹出滚轮选择器（日期 + 时间两级滚轮），不可手工输入，杜绝非法时间；系统自动校验"结束必须晚于开始""开始不得早于当前"，不合法时自动调整或拒绝；
- 保存草稿：表单校验通过后写入本地 SQLite 草稿箱，可在离线环境随时编辑；
- 保存并发布：先落草稿再同步服务器（MySQL 新增活动记录），发布成功后草稿标记"已发布"，不会重复发布；
- 草稿箱：每条未发布草稿可"载入表单""发布到服务器"或"删除"，发布以草稿自身内容为准；删除有二次确认（本地草稿无云端备份）；
- 草稿载入表单：点"载入表单"把草稿回填到上方表单，表单进入编辑态（提示"正在编辑草稿 #n"），再次保存是**更新该草稿**而不是新建一条；发布成功后自动退出编辑态；点"退出编辑 / 清空表单"可放弃；
- 已发布活动管理：页面底部列出全部已发布活动（**含已下线**），每条可"编辑""下线 / 恢复上线"，点击活动名进入详情；下线后误操作可自行恢复，无需改数据库。

> 说明：草稿保存不校验"开始时间必须晚于当前"（允许补录历史活动的草稿），点"保存并发布"时才校验并由服务端复核。

### 5.6.1 编辑活动

在"发布活动 → 已发布活动"或活动详情页点"编辑活动"进入编辑页：回填当前标题 / 内容 / 地点 / **类别** / 时间 / 学时 / 人数上限后保存，调用 `/api/activity/update` 在原记录上更新。规则：

- 允许保留早于当前的开始时间（便于修正历史活动的文案），但结束时间必须晚于开始时间；
- 人数上限不得小于当前有效报名数（页面会提示"当前有效报名 N 人"），服务端同样校验并返回实际人数；
- 改类别只影响**之后**审核通过的学时规则（类别上限按新类别计算），已认定学时不会被追溯改动；
- 已产生的报名记录与已认定学时不受影响；活动处于已下线状态时仍可编辑。

### 5.7 审核中心

审核中心为管理员功能，筛选与分页都在服务端执行：可按"全部 / 待审核 / 已通过 / 已驳回"筛选、按**活动下拉**（含已下线活动）过滤、按**姓名 / 学号 / 活动名关键词**搜索，三项条件可叠加；列表 20 条/页，底部提供"上一页 / 下一页 · 第 P 页 · 共 N 条"。对待审核记录点击"通过"或"驳回"：**通过按钮会直接显示本次将认定的学时（取该活动学时，而非报名记录当前的 0）**，通过时服务器自动把该活动学时累计进该成员学时汇总（事务保证不重复累计）；驳回则记录状态与备注。交互细节：

- **分类与学时上限**：每条记录显示活动类别徽标与活动原学时。通过时服务端按 `sys_config` 的规则依次裁剪——先按"单活动上限"（`rule.<类别>.max_activity`）截断，再按"类别累计上限"（`rule.<类别>.max_total`）扣除该生该类别已认定学时，结果为 0 时仍通过但记 0 学时并在备注追加"超出「XX」类别上限"。规则默认全为 0（不限），因此基线数据不受影响；审核结果提示会明确写出"已按规则折算"；
- 通过/驳回均弹出确认对话框，防止误触（驳回后成员需重新报名，操作不可逆）；
- 已审核的记录在服务端层面禁止重复审核（返回"该记录已审核，不能重复操作"）；审核本身为"事务内锁报名行 + 条件更新（status=0）+ 影响行数校验"，即使两位管理员同时点通过（或网络重试）也只会累计一次学时；
- **列表过期不会静默失败**：若成员在管理员点"通过"之前撤销了报名，服务端返回"该报名已被学生撤销或不存在，请刷新列表"，页面同时弹出 toast 并在操作区显示红色错误提示（不再是一行灰字）；
- 审核结果在成员端"我的报名"同步后可见。

审核中心顶部有**"报名审核 / 注册申请"两个页签**。切到"注册申请"可看到自助注册的待审清单（学号、姓名、班级、注册时间），对每条点"同意"或"拒绝"：同意后该学生立即可登录，拒绝则保留记录但禁止登录。已加入的成员在"注册申请"里不再出现（只列待审/待处理项），其完整信息与注销入口统一在"用户管理"页。

### 5.8 服务器实时日志

服务器实时日志为管理员功能，默认每 3 秒自动刷新，展示最近若干条请求（时间精确到毫秒、方法、路径、状态码、耗时、来源 IP）。支持按"全部 / 失败 / 慢请求"与"ALL / GET / POST"两组条件筛选，并可输入路径关键词（如 `/api/signup`）过滤；慢请求（≥500ms）额外标"慢"。每次 App 请求服务器都会实时出现在此处，同时写入 MySQL 的 request_log 表，可直接用 SQL 查询核验。可切换手动刷新。

### 5.9 设置

设置页可修改服务器地址（IP + 端口），**无需登录即可访问**（引导页"设置"入口恒在）。保存时会校验：地址不能为空、不能带 `http://` 或空格，端口必须是 1~65535 的整数；点"测试连接"会先保存当前输入再探测，避免改完地址却测到旧地址。模拟器联调用 10.0.2.2:8000；真机演示需改为宿主机局域网 IPv4（如 10.15.85.109）并保证同一局域网、服务器已放行 8000 端口。页面提供"测试连接"按钮与当前账号信息、退出登录（退出时同时请求服务端注销 Token，避免旧 Token 在 24 小时有效期内继续可用）；连接失败时也可在此修改地址后重新测试。退出登录（含主界面"我的"页退出）会先请求服务端注销 Token，再**清空返回栈**回到引导页，不会停留在已失效的主界面；Token 过期或服务端重启导致的 401 会自动清除本地登录态并提示重新登录。

设置页还包含两处与演示直接相关的能力：

- **模拟刷卡（仅管理员）**：选择"未结束且未满"的活动后点"模拟刷卡"，走的是与 ESP32 完全相同的 `/api/signin` 接口（不是本地假数据），因此 ESP32 硬件不在场时也能完整演示"刷卡→签到→累计学时→双端可见"这条链路；
- **危险操作（仅普通成员）**：见 5.11 账号注销。

### 5.10 用户管理

入口：管理 Tab → "用户管理"（第二位卡片）。这是管理员的**全量学生视图**，与审核中心的分工是：审核中心处理"待办的事"，用户管理查看"全部的人"。

- 顶部：返回、标题"用户管理"、"共 N 人"（随筛选结果变化）与刷新按钮；
- **分组查找**：六个分组标签以 2 行 3 列排布（避免横向滚动被裁切），分别是"全部 / 待审核 / 已通过 / 已驳回 / 已达标 / 未达标"，每个标签带实时人数。分组在**服务端**过滤（不是先拉全量再前端筛），因此 `total` 与列表行数始终一致，不会出现"翻页少人"；
- **关键词搜索**：支持学号、姓名、班级，与分组条件叠加生效（如"未达标 + 计科"）；
- **学生卡片**：姓名、注册状态徽标（待审核/已通过/已驳回，颜色区分）、学号·班级、右侧学时摘要与达标进度条（未设达标线时显示"未设置"）、RFID 卡号（未绑卡显示"未绑卡"）、注册日期（只到日）；
- **注销入口**：每张卡片右下角"注销"，点开在当前卡片下**内联展开**确认面板（同一时刻只展开一个，避免误点多个），面板如实列出"将删除报名 M 条、学时 X"，并要求输入该生学号后才可点"确认注销"。详见 5.11。

> 排序规则：待审核优先（管理员需要先处理它们），其余按学时降序，因此"谁学时最高"在列表里一眼可见。

### 5.11 账号注销

系统提供两条注销通道，**都是不可逆的硬删除**（不是标记删除、不是隐藏）：

| 通道 | 入口 | 操作人 | 可注销对象 |
|---|---|---|---|
| 学生自助注销 | 我的 → 设置 → 危险操作 → 注销账号 | 本人 | 仅本人 |
| 管理员注销 | 用户管理 → 卡片"注销" | 管理员 | 任意学生 |

**操作流程（两步，先看清再动手）**

1. 点注销后先向服务端查询**影响面**（`GET /api/student/impact`），页面如实展示：报名总条数、其中已通过/待审核/已驳回各几条、已认定学时合计、注册状态。学生端需先点"注销账号"才展开，管理员端在卡片内联展开；
2. **学生输入本人登录密码**才激活"确认注销"按钮；**管理员输入该生学号**即可（两条通道的确认要素不同）。
   - 学生侧为什么不用学号：学号在学时排行、用户管理里都是公开信息，拿它当凭据等于没有确认。Token 一旦泄露（手机丢失、共享设备未退出），攻击者用公开学号就能一键把账号连同报名与学时物理删除；密码是唯一"只有本人知道"的要素。
   - 密码校验在服务端**事务内、`FOR UPDATE` 锁行之后**完成，不存在"校验通过→删除之间被并发改密"的窗口；连续 5 次密码错误触发 60 秒节流（按 IP + 学号），防止持 Token 者暴力猜密码。
   - 管理员侧仍用学号：管理员本来就有删除权限，这里的学号只是防手滑。
   - 双重校验：前端按钮禁用 + 服务端二次校验，绕过 UI 直接打接口同样会被拒。

**注销后数据如何处理（这是本功能的重点）**

服务端在一个事务内按 `signup → hours_total → student` 顺序级联删除，任一步失败整体回滚，不会留下半条数据：

- **报名记录**：该生全部报名（含已通过、待审核、已驳回）一并删除，活动名额随之释放；
- **学时汇总**：`hours_total` 中该生的汇总行删除，排行榜与报表立即不再出现该生（排行榜是动态查询，不做缓存）；
- **账号本体**：`student` 行删除，其学号可从"用户管理"和登录入口彻底消失；
- **登录态**：该学号名下所有 Token 立即回收，其他设备上仍在登录的会话下次请求会收到"登录已失效"并自动清除本地登录态（不会出现"看着已登录、点什么都没反应"）；
- **本地缓存**：App 端同时清掉本地 `local_signup` 中该学号的历史报名缓存，避免注销后本地还显示旧记录；
- **审计日志保留**：`request_log` 表**不删**（无外键关联），注销动作本身以 `AUDIT` 标记留痕，便于事后追查"谁在什么时候注销了谁"；
- **RFID 卡号自动解绑**：刷卡逻辑按卡号反查学生，学生行删除后该卡自然失效（返回"卡号未绑定任何成员"），卡片可重新绑定给新账号；
- **学号可复用**：注销是物理删除，同一学号可以重新注册（重新走注册审批流程），不会与历史数据冲突。

**并发安全**：注销时对 `student` 行加 `FOR UPDATE` 行锁，实测 4 路请求同时注销同一账号，恰好 1 个成功、其余返回"该学号不存在或已注销"，三张表零残留。

**演示建议**：先演示"学时报表双端一致"（20.5 学时基线），再演示注销。注销后学时总额会下降（被注销人的学时被真实移除），这是设计如此而非数据错误——如担心评审误解，可先说明"接下来演示注销，总额会同步减少"。

### 5.12 错误提示与失败反馈

系统的原则是**不存在静默失败**：任何写操作（报名、撤销、审核、发布、编辑、注销、设置达标线…）只要没达到预期结果，都会给出可读的中文原因。

- **全局 toast**：所有 POST 操作失败自动弹出 3 秒 toast（底部浮动），批量操作（如"全部通过"）内部调用传静默参数，只汇总统计不逐条刷屏；
- **服务端消息中文化**：业务错误消息全部为中文，例如"该报名已被学生撤销或不存在, 请刷新列表""名额已满, 无法报名""活动未开放报名""活动不存在或已下线""该学生不存在或已注销""数据库连接失败, 请检查 MySQL 服务"；
- **页面级红字**：审核中心等页面的操作结果区在失败时染红加粗并允许两行，与成功提示在视觉上区分；
- **登录失效自动兜底**：服务端约定"业务错误也走 HTTP 200，错误码在响应体"，App 端因此同时检查 `HTTP 401` 与响应体 `code==401`，命中即清除本地登录态并提示重新登录（这是历史上一处真实缺陷，已修）。

**典型场景**：成员报名后管理员未刷新列表，成员在此期间撤销报名，管理员再点"通过"——页面会弹出"该报名已被学生撤销或不存在，请刷新列表"，而不是无反应；同时学生学时、活动名额都不受影响。

### 5.13 现场签到码与签退（防转发作弊）

与 RFID 刷卡并存的第二套签到方式，用于"没有读卡器 / 需要现场核验"的场景：

1. **管理员出示签到码**：进入进行中的活动详情页，顶部出现"现场签到码"卡片，显示 6 位数字码与"本码剩余 N 秒"。码按 60 秒窗口轮换（HMAC-SHA256(服务端随机密钥, 活动 ID + 窗口) 取 6 位），页面每秒本地倒计时、归零自动换新码；也可点"立即刷新"立刻取当前码。服务端密钥在进程启动时随机生成，**重启后旧码全部失效**；
2. **成员输码签到**：报名审核通过后，活动详情页出现"输入 6 位签到码"输入框与"签到"按钮；输入管理员出示的码提交，服务端接受当前窗口及上一窗口（前后各留 60 秒宽限，避免临界点误判）。无报名记录时自动建立并通过（等同现场签到），待审核则自动通过并签到，已驳回则拒绝并提示原因；同一成员重复提交幂等，不会重复计学时；
3. **签退与学时折算**：签到后按钮变为"签退"，点击写签退时间。服务端按"实际在场分钟 ÷ 计划时长"折算本次学时，`min(1, 比例)` 截断，结果取 0.5 的整数倍，下限 0.5 学时；未签退（仅 RFID 单点签到）时仍按活动全额学时认定，**因此不改变原有演示基线**；
4. **活动结束后**：管理员不再显示签到码卡片，成员未签到时提示"活动已结束, 未签到不再补记学时"；已签到的成员仍可签退（用于活动刚结束的收尾）。

> 为什么不用固定码：固定签到码截图转发即可代签，且无法约束在场时长。60 秒轮换 + 签退折算让"把码发到群里"既来不及、也拿不到全额学时。

### 5.14 深色模式

全应用颜色统一走设计 token（`Theme` → `resources/base|dark/element/color.json`），跟随系统深浅色自动切换：背景、卡片、分隔线、正文/次要文字、主色、成功/危险/签到色均有深色对应值，深色下不再出现"白底刺眼、浅灰字看不清"。状态栏与启动窗口背景同步适配；所有页面（登录、广场、详情、报表、审核、日志、设置）共用同一套 token，新增页面无需单独适配。

### 5.15 学时申诉（v4.0）

**成员发起**：我的报名 → 已通过记录 → "学时申诉" → 填写理由（至少 5 个字，如"实际到场 1.5 小时只记了 0.5 学时"）→ 提交。同一报名同时只能有一条待处理申诉；已通过/已驳回后可再次申诉。

**管理员处理**：审核中心 → "学时申诉"页签（带待处理角标）。每条申诉显示成员、活动、申诉前认定学时、活动学时与理由：

- **通过并调整学时**：可把认定学时改为 `0 ~ 活动学时` 之间（`0.1` 精度），提交后系统在同一事务内更新报名明细并按明细重算该成员学时汇总，报表立即生效；
- **驳回**：必须填写原因（学生端可见），不清零、不改动已认定学时；
- 已处理记录显示"复核结果/驳回原因 + 处理人 + 处理时间"，全过程留痕；并发处理只会有一次生效（条件更新 `WHERE status=0`）。

### 5.16 学时规则（v4.0，仅管理员）

设置 → "学时规则"卡片：七大类各两列——**单活动上限**、**类别累计上限**，`0` 表示不限，取值 `0~999` 的整数。

- 审核通过时依次执行：`本次学时 = min(活动学时, 单活动上限)` → 再按该生该类别已认定合计裁剪到 `类别累计上限`；结果为 0 仍通过，备注注明"超出类别上限"；
- 保存后**下一次审核立即生效**（服务端每次审核实时读配置，无需重启）；
- 服务端对类别 key 与数值做白名单校验，未知类别/负数/超范围会整体拒绝（不会"改了一半"）；
- 演示建议：把"志愿公益"的类别累计上限设为 `10`，再审核一条大额志愿活动即可看到裁剪效果。

### 5.17 签到异常检测（v4.0，仅管理员）

学时报表 → "异常检测"页签，三类只读风险清单：

| 类型 | 判定 | 提示含义 |
|---|---|---|
| 批量签到 | 同一活动 10 分钟窗口内签到 ≥ 5 人 | 疑似代签/批量刷卡，建议核对现场 |
| 长期未签退 | 签到超过 24 小时仍未签退 | 学时按全额认定偏高，提醒补签退或复核 |
| 学时超限 | 认定学时 > 活动学时 | 历史脏数据/手工改库，可用申诉复核或"重算学时"修正 |

顶部三个计数块可一眼看出风险分布；页签内容可导出 CSV（前两类含成员与时间，第三类含超出学时）。

### 5.18 社团主页与社长换届（v5.0）

入口：**管理 → 社团主页**（社团账号可见；平台管理员没有"本社团"，会显示提示而非空页面）。

页面分四个区块：

1. **社团信息卡**：社团名称、登录账号、挂靠单位、简介、现任社长与在任天数（`leader_since` 起算），以及成员数 / 活动数 / 报名数 / 已认定学时汇总。
2. **社长修改入口**：内联展开表单，填写新社长姓名、学号（留空表示沿用上一任学号）、备注，并**必须输入当前社团账号密码**确认；提交前弹出二次确认框，明确列出"原社长 → 新社长"。
3. **历任社长时间轴**：姓名、学号、任期起止、变更方式（换届 / 更正 / 初始化）、操作人、备注；`end_at` 为空的一条标记为「在任」，历史记录只追加不覆盖。
4. **权限继承说明卡**（常驻文案）：账号属于社团、权限随岗位不随人、换届不影响历史活动与学时、所有换届均留痕可查。

换届失败分支均给出明确文案：

| 情况 | 返回 | 提示 |
|---|---|---|
| 未填写新社长姓名 | 400 | 请填写新社长姓名 |
| 密码错误 | 403 | 登录密码不正确, 换届已取消（同时计入节流） |
| 社长已被他人变更 | 409 | 社长已被他人变更为「XXX」, 请刷新后重试 |
| 短时间连续失败 | 429 | 密码错误次数过多, 请 60 秒后再试 |

服务端在同一事务内先 `SELECT ... FOR UPDATE` 锁住社团行，再校验密码与 `expect_leader`，然后结束上一条在任记录、追加新记录、更新 `club.leader_name/leader_stu_no/leader_since`、并做社团岗位迁移。**换届只改这三列 + 一条历史，不签发新账号、不重建 Token**——新社长用同一账号密码登录即继承全部社团权限；并发提交时后到者拿 409，在任记录永远只有一条。

遗留说明：换届前请确认新社长学号正确，服务端会把它自动纳入社团成员（`club_member`）。

### 5.19 活动参与范围（v5.0）

发布活动（5.6）与编辑活动（5.6.1）新增**参与范围**分段控件：

| 取值 | 展示文案 | 谁能看到 / 谁能报 |
|---|---|---|
| `club` | 仅本社团 | 仅本社团在册成员可见、可报名；内部活动带「仅本社团」标签 |
| `all` | 全校开放 | 全部已通过审核的学生可见、可报名 |

> 默认值刻意不同向：**数据库列默认 `'all'`**（历史活动语义不变，守住演示基线），**发布页默认选中「仅本社团」**（新建活动默认收紧）。两处代码都有注释说明原因，请勿"顺手统一"。

范围校验在服务端，且**前置到产生数据之前**：

- 列表只返回有权查看的活动（学生：`join_scope='all'` 或 `club_id` 属于本人社团集合；社团管理员：仅本社团；平台管理员：全部）；
- 外社团学生直接请求 `/api/signup/add` → 403；
- 外社团学生用转发来的签到码 `/api/signin/code` → 403，**且不产生报名行、不增加学时**（这是 v5.0 修复的核心越权点）；
- 外社团学生刷卡 `/api/signin` → 403；
- 公开活动满员仍返回 403，跨社团同时间段报名仍按**全局**校验返回 409（不能靠"分社团"绕过时间冲突）。

公开活动引来外社团报名后，审核中心（5.7）的报名卡片会标记「外社团」，审核权归活动所属社团。活动从"全校开放"改回"仅本社团"时，详情提交后会提示已有多少外社团成员报名——**存量报名与已认定学时保留**，只影响后续新报名。

### 5.20 社团成员管理（v5.0）

入口：**管理 → 用户管理 → 社团成员**（社团账号看到的是本社团在册成员，平台管理员仍是全量学生口径）。

- 顶部三个计数块显示社长 / 部长 / 成员人数与在册总数；
- 支持按岗位（社长 / 部长 / 成员）与状态（在册 / 已退出）筛选，按姓名或学号搜索；
- 每行可"移除"，内联二次确认：移除只置 `status=0` 并写 `quit_at`，**学生账号、历史报名与已认定学时全部保留**，重复移除不会报错；
- **现任社长不能直接移除**（返回 400 并提示先完成换届），避免社团的 `leader_name` 指向一个已退社的人。

### 5.21 通知公告（v5.0）

入口：**管理 → 通知公告**（管理员）/ 我的 → 通知公告（成员）。

- 社团账号发布的公告归属本社团（`club_id` 只取 Token，不接受请求体指定）；平台管理员可显式指定社团；
- 支持**置顶**（列表按 `top_flag DESC, created_at DESC` 排序）；
- 支持**撤回**与恢复：撤回后成员端列表不再出现，社团管理员仍能看到该条并显示状态；
- 成员端显示未读角标（`unread_count`），打开某条即标记已读（`announcement_read` 幂等写入，重复标记不报错）；
- 学生只能看到**本人所属社团**且已发布的公告，跨社团公告对其不可见。

### 5.22 社团维度统计（v5.0）

入口：**学时报表 → 社团维度统计卡**（仅社团账号显示）。

| 指标 | 口径 |
|---|---|
| 仅本社团 / 全校开放活动数 | `activity.club_id = 本社团` 且按 `join_scope` 分组 |
| 通过率 | 已通过报名数 ÷ 报名总数 |
| 外社团参与 | 报名人**不在本社团在册名单**中的去重人数与报名条数（只可能来自全校开放活动） |

口径要点：**学时归属"活动所属社团"**，统计一律按报名时快照的 `signup.club_id` 聚合；`hours_total` 仍是全局主键 `stu_no` 的学时汇总，不是"每个社团各自一份学时"。服务端 `/api/stats/club` 用单条聚合 SQL 一次算完，并附学时分布分档与报名最多的 5 个活动。

### 5.23 社团注册（v5.0 重构，公开）

入口：**登录页 → "是社团? 注册社团(提交管理员审核)"**。

- 表单：自设登录账号、社团名称（均唯一）、登录密码（6~64 位，二次确认）、挂靠单位、社团简介、首任社长姓名/学号（选填，留痕用）；
- 提交后 `status=0` 待审核，**审核通过前登录会提示「社团注册申请待管理员审核」**；账号与社团名在待审期间同样占用，防止审核通过后撞名；
- 注册人视为首任社长：审核留痕在注册时即落库一条 `change_type=3` 的历任社长记录；
- 平台管理员在「管理 → 社团审核」处理：**通过**（分配独立编号 `#club_id`，即可登录）/ **驳回**（必填理由，登录提示「已被驳回」）；另可对正常社团**停用**（必填理由）与**恢复**；
- 状态机：`0 待审核 → 1 正常 → 3 已停用 →（恢复）1`，`0 → 2 已驳回`；全部动作走条件更新，重复操作返回 409 并在卡片上显示当前状态。

### 5.24 社团广场与入社/退社审批（v5.0 重构）

**成员端（我的 → 社团广场）**：

- 「全部社团」页签：浏览/搜索全部正常社团（名称/简介/挂靠单位/社长/成员数/活动数），点「申请加入」提交申请；可同时申请加入多个社团；
- 「我的社团」页签：已加入与审核中的社团；已加入的社团可「申请退出」；
- 个人状态标签与服务端口径一致：`已加入 / 申请审核中 / 申请被驳回 / 已退出 / 退出审核中`；**退出审核期间成员身份仍有效**（内部活动仍可见），审批通过才真正退出；
- 判据全部在服务端：不在册学生看不到内部活动，审批通过即刻可见；退出审批通过即刻不可见；历史学时永久保留。

**社团账号端（管理 → 用户管理 → 入社/退社审批区）**：

- 默认只看待审申请，可切换「查看全部」；每条申请显示类型（加入/退出）、申请人、理由、时间与**「已加入社团」参考信息**（申请人当前在册的其他社团，审批人据此评估）；
- 「同意」直接生效：加入 → 入册（曾退出的可复入，原岗位保留）；退出 → 置离册（学生账号与学时保留）；
- 「驳回」必填理由（内联输入框，为空不可提交）；
- 服务端兜底：现任社长不可退出/被移除（400）；跨社团申请 403；重复审批 409（并发恰一次）；学生注销后其申请自动清理。

## 6 验收演示流程

建议按以下顺序演示，覆盖"报名 → 同步 → 服务端审核 → 学时累计双端一致"的完整链路：

| 步骤 | 操作 | 查验点 |
|---|---|---|
| 1 | 冷启动看到引导页 → 以普通成员 2023001（张三）登录 → 进入"活动"Tab | 引导页显示服务器在线；登录后直接进主界面；活动列表来自服务器 MySQL |
| 2 | 进入任一活动点击"立即报名" | App 提示已写入本地 SQLite 并同步服务器；本地库可查 |
| 3 | 在"我的报名"页查看记录 | 状态为"待审核(已同步)"；本地 SQLite 有记录 |
| 4 | 退出登录，以管理员 admin 登录进入审核中心 | 报名记录出现在待审核列表（来自服务器） |
| 5 | 点击"通过" | 提示自动累计学时；学时报表出现该成员学时 |
| 6 | 以张三重新登录，查看"我的报名"（进入即自动同步）与"学时报表" | 状态变为"已通过"；报表双端对比卡下方显示"✔ 双端一致"（若本地缓存滞后，点"校准本地缓存"后一致） |
| 7 | 管理员查看"服务器实时日志" | 上述全部请求实时可见；MySQL request_log 可 SQL 查询 |
| 8 | 管理员进入"用户管理" | "共 N 人"；切"待审核"分组数量与注册审批待办一致；搜索班级（如"计科"）与分组叠加生效 |
| 9 | （可选）演示注册审批：新学号注册 → 管理员"注册申请"页签同意 → 新账号可登录 | 同意后立即可登录；"管理"Tab 角标数随之减少 |
| 10 | （可选）管理员进入进行中活动详情，出示"现场签到码"；成员（已通过报名）在详情页输码签到 → 签退 | 码每 60 秒变化；签到后状态变"已签到"；签退后显示按在场时长折算的学时（下限 0.5） |
| 11 | （可选）管理员报表页切"预警"页签 → 导出 CSV | 名单按缺口降序；系统文件选择器保存后可直接用 Excel 打开 |
| 12 | （可选）v4.0 申诉：成员在"我的报名"对已通过记录发起申诉 → 管理员在审核中心"学时申诉"页签通过并调整学时 | 报表学时立即变化；两条记录均留痕（申诉人/处理人/时间） |
| 13 | （可选）v4.0 规则：设置 → 学时规则，把"志愿公益"累计上限设为 10 → 审核一条大额志愿活动 | 认定学时被裁剪到不超过剩余额度，备注注明超出上限 |
| 12 | （可选）演示注销：管理员在用户管理 → 目标学生"注销" → 展示影响面 → 输学号 → 确认；（学生自助则在设置页输本人登录密码） | 列表刷新、人数减 1；该生从排行榜消失；其旧 Token 立即失效；活动名额同步回补 |

## 7 嵌入式扩展项：ESP32 + RFID 刷卡签到

ESP32 通过 SPI 连接 MFRC522 读卡模块，刷卡后把卡号上报服务器，服务器按卡号匹配学生并完成签到与学时认定。此扩展项可脱离 App 独立演示，与 Web 端数据互通。

### 7.1 硬件接线

| MFRC522 引脚 | ESP32 引脚 |
|---|---|
| SDA (SS) | GPIO5 |
| SCK | GPIO18 |
| MOSI | GPIO23 |
| MISO | GPIO19 |
| RST | GPIO27 |
| 3.3V | 3.3V |
| GND | GND |

### 7.2 配置修改

修改 esp32_rfid\rfid_esp32.ino 顶部的配置区：WiFi 名称与密码、服务器地址（SERVER_BASE，填宿主机局域网 IPv4:8000）、要签到的活动 ID（ACTIVITY_ID，需为已发布且未结束的活动）。编译烧录后打开串口监视器，即可看到刷卡上报结果。固件已做两处现场保护：WiFi 掉线每 5 秒自动重连（无需重启设备）、同一张卡 5 秒内不重复上报（卡一直放在读头上也不会刷屏）。

若希望限制"只有本终端能刷卡"，可给服务器加设备密钥：启动时追加第 5 个参数或设置环境变量 `CLUB_DEVICE_KEY`，例如 `server.exe 8000 root 123456 127.0.0.1 club-rfid-2026`，同时把固件里的 `DEVICE_KEY` 改成相同值；此后未带正确 `X-Device-Key` 头的刷卡请求会被拒绝（返回 401）。不配置则保持原行为（不校验）。

### 7.3 签到认定逻辑

服务器对刷卡请求按卡号匹配学生后：若该活动无报名则自动创建并通过（到场认定）；若报名待审核则置为通过并认定学时；若已通过则仅标记签到；若报名已被管理员驳回则拒绝签到（提示需先重新报名），避免刷卡绕过人工审核；活动已下线或已结束则拒绝认定。学时累计为事务操作，且"待审核→通过"的更新带 `status=0` 条件与影响行数校验，重复刷卡、并发刷卡都不会重复累计。**注意：如果活动中没有报名记录，刷卡会自动建一条已通过记录，因此演示"刷卡签到"时应先确认该活动的报名情况，或在演示前说明这一"到场认定"设计。**

## 8 常见问题（FAQ）

| 问题 | 原因与解决办法 |
|---|---|
| App 提示"无法连接服务器 / Operation timeout" | 检查服务器是否已启动且监听 0.0.0.0:8000；App 设置页服务器地址是否为 10.0.2.2（模拟器）或宿主机局域网 IPv4（真机）；Windows 防火墙是否放行 8000 端口 |
| 真机连不上服务器 | 手机与电脑需在同一局域网；服务器地址填电脑的局域网 IPv4（可在设置页查询）；服务器需 bind 0.0.0.0 |
| 登录提示"未登录或登录已过期" | 服务器重启后内存 Token 失效，退出重新登录即可 |
| 活动时间无法输入 | 发布时间采用滚轮选择器，仅能滚动选择并自动校验"结束晚于开始、开始不早于当前"，无法手工输入非法时间 |
| 重复报名会重复吗 | 不会。本地按 client_id 幂等、服务器按唯一键去重，重复点击只保留一条记录 |
| 审核通过后学时没变 | 学时累计在服务器事务内完成，刷新"学时报表"查看；成员端点击"我的报名→同步服务器状态"刷新本地 |
| 刷卡提示"该报名已被管理员驳回" | 驳回是管理员的人工决策，刷卡不会绕过审核；成员需在活动详情页点击"重新报名"，管理员通过后再刷卡签到 |
| 刷卡提示"活动已结束, 不能再刷卡认定学时" | 活动结束时间已过，出于数据可信性不再接受签到；如需补录请由管理员调整活动时间或直接审核报名 |
| 报名成功后提示"仅本地(未同步)" | 服务器当时不可达（地址错误/未启动）。修正服务器地址后，在"我的报名"点"立即补传"或重新进入页面，会自动补传；服务端按 client_id 幂等，不会重复报名 |
| 提示"登录失败次数过多, 请 60 秒后再试" | 同一账号 60 秒内连续输错 5 次会临时锁定（防暴力猜测），等待 60 秒或重启服务端即可恢复 |
| 学时汇总与实际认定不一致 | 管理员进入"学时报表"点"重算学时"，服务器会以已通过的报名记录重建 hours_total |
| 运行 test_api.py 会不会清掉演示数据 | 默认不会（保留现有数据）；只有显式加 `--reset` 参数才会把 signup 重置为待审核并清空 hours_total |
| 历史版本"审核中心闪退" | 已修复：页面状态改为显式过滤渲染，不依赖列表下标直接索引；当前版本可稳定使用 |
| MySQL 数据如何查验 | 连接 club_system 库查询 activity / signup / hours_total / request_log 各表即可；验收演示建议展示 hours_total 与 request_log |
| 注销后同一学号还能再注册吗 | 能。注销是物理删除（报名、学时、账号本体一并清除），学号可重新走注册审批流程 |
| 注销后学时总额变少了，是数据错了吗 | 不是。注销会真实删除该生的学时记录，总额同步下降；排行榜与报表均为动态查询，无残留 |
| 管理员点"通过"提示"该报名已被学生撤销或不存在" | 列表是点击前的快照，成员在此期间撤销了报名。点刷新即可，学时与名额均未受影响 |
| 导出的 CSV 用 Excel 打开中文乱码 | 导出时已写入 UTF-8 BOM，正常双击不应乱码；若仍异常，请用 Excel"数据 → 从文本/CSV"导入并选择 UTF-8 |
| 关掉服务端窗口后 App 提示登录失效 | 服务端 Token 存于内存，重启即清空。重新登录即可；演示期间请不要关闭该窗口 |
| 演示前怎么确认数据没被测试脚本改坏 | 在 server 目录执行 `python verify_demo_data.py`，应输出 8 活动 / 19 报名 / 5 人 / 20.5 学时；详见第 9 节 |
| 真机 `hdc install` 报签名错误 | 当前产物是 unsigned HAP，只能装模拟器；真机需在 DevEco 配置自动签名后重新构建（见 3.3） |
| 服务端启动窗口一闪就没了 | 说明 MySQL 未启动或 exe 被占用；`start_server.bat` 会先检测 3306 并停住显示原因，按提示启动 MySQL 服务即可 |
