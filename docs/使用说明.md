# 社团活动报名与学时认定系统 使用说明

题号 86 · HarmonyOS 课程设计（SQLite 本地库 + 服务端 MySQL）· 文档对应版本 **v3.0**（服务端 `/api/health` version 3.0）

> 完整 Word 版使用说明见仓库根目录：`使用说明文档.docx`（随项目本地交付）。本 Markdown 为同源可读版本，两者内容一致。

## 1 系统概述

### 1.1 功能简介

本系统面向高校社团的活动组织与学时认定管理，提供"活动发布—报名—审核—学时认定—统计报表"的完整闭环，并支持 RFID 刷卡签到作为嵌入式扩展项。主要功能如下：

- 注册与审批：成员自助注册（学号 + 姓名 + 班级），管理员在审核中心"注册申请"页签同意或拒绝；
- 活动发布：管理员创建活动（名称、内容、地点、时间、学时、人数上限），支持本地草稿保存与一键同步发布到服务器；
- 活动报名：普通成员浏览活动并报名，报名记录同时写入本地 SQLite 与服务器 MySQL，重复报名自动幂等去重；
- 审核认定：管理员在审核中心对报名记录"通过/驳回"，通过后服务器自动累计学时到学时汇总表；
- 用户管理：管理员查看全系统学生信息，按注册状态与学时达标情况分组，支持按学号 / 姓名 / 班级搜索；
- 账号注销：成员可在设置页自助注销本人账号，管理员可在用户管理页注销任意学生；注销为事务级联删除（报名、学时、登录态一并清除）；
- 学时报表：提供成员排行与认定明细，本地 SQLite 统计与服务器 MySQL 统计双端对比；
- 服务器实时日志：每次请求实时记录（内存日志 + MySQL request_log 双写），管理员可在线查看；
- 失败反馈：所有写操作失败都会给出明确中文原因（弹窗 toast + 页面红字），不存在"点了没反应"的静默失败；
- 嵌入式扩展：ESP32 + RFID 读卡器实机刷卡签到，到场即认定学时（扩展项）。

### 1.2 系统架构

系统采用"鸿蒙 App + 本地 SQLite + 自主 C++ Web 服务器 + MySQL"的双通道架构：App 端使用 HarmonyOS 关系型数据库（relationalStore）本地落库，保证离线可查；同时通过 HTTP 接口与自主编写的 C++ Web 服务器（监听 0.0.0.0:8000）同步数据，服务器以 MySQL 8.0 作为服务端持久化存储。数据一致性通过"本地唯一 client_id 幂等 + 服务端唯一键（uk_client、uk_act_stu）去重 + 事务化容量/学时累计"三层机制保证。

### 1.3 权限体系

系统明确区分两类角色，权限由服务端按登录 Token 统一校验，App 端同时做页面级守卫：

| 角色 | 登录方式 | 功能范围 |
|---|---|---|
| 管理员 | 账号 + 密码（admin_user 表） | 发布/编辑/上下线活动、审核报名与注册申请（通过自动累计学时）、用户管理（含注销学生）、查看服务器实时日志、全量学时报表与达标线设置 |
| 普通成员 | 学号 + 姓名（student 表） | 浏览活动、报名/撤销、查看我的报名与本人学时明细、查看学时排行、注销本人账号 |

## 3 快速启动

### 3.1 初始化数据库

在 MySQL 中执行建库脚本，脚本会自动创建 club_system 库及全部表，并写入演示数据：

```
mysql -u root -p123456 --default-character-set=utf8mb4 -e "source C:/Users/34520/Desktop/chapter03/server/init_db.sql"
```

### 3.2 编译并启动服务端

编译命令（Windows）：直接双击运行 `server\build.bat`，脚本会按顺序尝试 Dev-C++ 自带 MinGW64（TDM）、Dev-C++（Program Files）与 PATH 中的 g++，取首个编译成功的工具链，统一使用 `-std=c++14`。

若手工编译，等价命令为：

```
g++ -std=c++14 -O2 -Wall server.cpp -o server.exe -I "C:\Program Files\MySQL\MySQL Server 8.0\include" -L "C:\Program Files\MySQL\MySQL Server 8.0\lib" -lmysql -lws2_32
```

> 注意：部分 MinGW 为 win32 线程模型，缺少 `std::thread` / `std::mutex` 实现，编译会报 `'thread' is not a member of 'std'`；此时请使用 Dev-C++ 自带的 TDM g++（脚本已自动优先选用）。编译前需先关闭正在运行的 `server.exe`，否则文件被占用会导致链接失败。

编译成功后运行 server.exe，服务器监听 0.0.0.0:8000。验证：浏览器访问 http://127.0.0.1:8000/api/health 应返回 {"code":0,...}，其中 `db:true` 表示 MySQL 连接正常、`version` 为服务端版本（当前 3.0）。

**日常启动推荐双击 `server\start_server.bat`**：脚本已写死 `cd /d "%~dp0"`（避免当前目录不是 server 导致找不到 libmysql.dll），启动前先探测 3306 端口确认 MySQL 已运行，再以 `server.exe 8000` 启动。参数与手工命令行完全一致（端口 8000、MySQL 127.0.0.1:3306、root）。**这个窗口需要一直开着**，关窗口或 Ctrl+C 即停止服务。

> 注意：服务端登录 Token 保存在内存中，**每次重启都会清空**，App 端会收到"登录已失效"并自动清除本地登录态，重新登录即可（不是故障）。因此演示过程中不要重启服务端。

### 3.3 构建并安装鸿蒙 App

在工程目录（chapter03\chapter03）执行：

```
hvigorw assembleHap --mode module -p product=default --no-daemon
```

产物位于 entry\build\default\outputs\default\entry-default-unsigned.hap，使用 hdc 安装到模拟器：

```
hdc install -r entry-default-unsigned.hap
```

> **真机安装需先签名**：当前构建为 unsigned HAP，可直接装入模拟器；装真机需在 DevEco Studio 的 `File → Project Structure → Signing Configs` 勾选自动签名（登录华为开发者账号后由 IDE 生成调试证书），重新 `assembleHap` 后再 `hdc install`。若验收使用模拟器演示，可跳过此步。

### 3.4 启动与登录

在模拟器打开 App，默认服务器地址为 10.0.2.2:8000（模拟器访问宿主机的标准地址），无需修改即可联调。使用演示账号登录后按角色进入对应功能。

## 5 功能与操作说明

### 5.1 登录

冷启动进入**引导页**：顶部显示服务器在线状态（可点"点此重试"），下方是"登录 / 注册 / 设置"三个入口，底部为"登录"按钮。登录页顶部可切换"普通成员 / 管理员"两种身份，普通成员填写学号与姓名，管理员填写账号与密码，提交后由服务端校验并签发 Token，后续请求自动携带。登录成功后**清空返回栈**进入主界面（返回键不会退回登录页），功能入口按角色显示。登录卡片下方提供"还没有账号? 去注册"与"服务器设置"两个快捷入口，未注册或连不上服务器时无需退回引导页。

### 5.2 引导页与主界面

**引导页（冷启动第一屏）**：显示服务器在线状态（可点"点此重试"）与"登录 / 注册 / 设置"三个入口。设置入口恒在，未登录也能直接改服务器地址。已登录时顶部出现用户卡片（姓名 + 角色）与"进入主界面"按钮，底部主按钮同步变为"进入主界面 ›"。

**主界面（底部 TabBar）**：

| Tab | 可见角色 | 内容 |
|---|---|---|
| 活动 | 全部 | 活动广场（分页列表 + 下拉刷新 + 触底加载） |
| 管理 | 仅管理员 | 五张卡片：审核中心、用户管理、发布活动、学时报表、服务器实时日志 |
| 我的 | 全部 | 成员：我的报名 / 学时报表 / 设置 / 系统介绍；管理员：学时报表 / 设置 / 系统介绍；底部"退出登录" |

底部导航为自绘（不使用系统 Tabs），切换不销毁页面状态（分页与滚动位置保留）。**"管理" Tab 上带角标，数值 = 待审核报名 + 待审批注册**——管理员不必点进去才知道有活；顶部同时显示"有 N 条待办"直达卡片。切到"管理"时会重新拉一次待办，角标保持新鲜。

"系统介绍"进入引导页查看服务器状态、角色功能一览与验收流程，点"进入主界面"即可返回（不会在主界面栈里叠加重复页面）。管理员在"我的"页不显示"我的报名"（管理员无报名记录，报名审核在审核中心）。

### 5.3 活动广场与报名

活动广场是主界面第一个 Tab（不再有独立页面），从服务器分页拉取已发布活动（每页 10 条，滚动到底自动加载下一页，支持下拉刷新），顶部显示"共 N 个"，底部显示"上拉加载更多 / 已全部加载 (M 个)"，展示名称、时间、地点、报名人数与剩余名额。点击活动进入详情页：普通成员可点击"立即报名"，报名记录先写入本地 SQLite（离线可查），再同步服务器等待审核；若已报名则显示报名状态（待审核/已通过/已驳回）。重复点击不会产生重复记录（本地与服务器双重幂等）。

交互细节：
- **名额校验**：活动设置了人数上限且已报满时，报名按钮自动替换为"名额已满"提示，不可报名；容量统计在服务端事务内完成（先锁活动行再计数），并发报名不会超员；已驳回的报名不计入名额；**剩余名额由服务端计算后随列表下发**，App 与服务端判定口径完全一致；
- **结束时间校验**：活动结束时间已过时，详情页显示"活动已结束"并禁用报名（服务端同样拒绝，避免对历史活动补报名）；
- **驳回后可重新报名**：报名被管理员驳回后，详情页按钮变为"重新报名"，点击后服务器将原驳回记录重置为待审核，无需重新填写任何信息；
- 管理员进入详情页不显示报名按钮，额外提供"下线该活动"（软删除：活动不再出现在广场，历史报名与学时记录保留）；活动处于已下线状态时该按钮变为"恢复上线"，可原地恢复；
- **状态以服务器为准**：详情页每次进入都会向服务器确认本人的报名状态并回写本地，管理员审核通过/驳回后无需先到"我的报名"点同步，回来即是审核结果（本地 SQLite 与服务器保持一致）；
- 所有二级页面（详情、我的报名、审核中心、学时报表、日志、设置、发布）左上角均有"‹ 返回"，不依赖系统返回手势。

### 5.4 我的报名

展示当前成员的全部本地报名记录与状态。进入页面会自动补传未同步记录并静默拉取一次服务器审核状态，服务器存在而本地缺失的记录（如另一台设备报名或 RFID 刷卡自动创建）会自动补全到本地，保证双端一致；也可手动点"同步服务器状态"。已刷卡签到的记录会显示"已刷卡签到"标记（来自服务端 `checkin` 字段，同步后落本地库，离线也能看到）；"报名时间"取服务器记录的时间，与本机同步时刻无关。

两条与"离线可用"配套的能力：

- **未同步补传**：报名时若服务器不可达，记录会先落在本地 SQLite 并标记"仅本地(未同步)"，页面顶部出现"有 N 条报名仅存本地"提示与"立即补传"按钮；进入页面时也会自动尝试补传。服务端按 `client_id` 幂等，反复补传不会产生重复报名；
- **撤销报名**：仅"待审核"记录显示"撤销报名"按钮，确认后同时删除服务器与本地记录并释放名额；已通过（已认定学时）与已驳回记录不提供撤销，保证学时账目不可被成员单方面改动。

### 5.5 学时报表

页面顶部为"本地 SQLite 统计"与"我的服务器学时"双端对比卡片（管理员视角右侧卡片显示"服务器全量学时"合计）；下方提供"学时排行 / 认定明细"两个页签。普通成员仅看到本人明细，管理员可查看全量排行与明细。服务器学时由审核通过自动累计（hours_total 表）。

两张卡片下方是**双端一致判定**：相同时显示绿色"✔ 双端一致"，不同则显示"⚠ 本地缓存与服务器差 X 学时"并给出"校准本地缓存"按钮。校准时以服务器报名记录为准回填本地 SQLite（含审核状态、学时、刷卡标记），之后本地统计即与服务器一致——这是验收"学时累计双端一致"最直接的演示入口。

管理员可设置**学时达标线**（页面"达标线"输入框 + 保存，写入服务端 `sys_config.required_hours`，0 表示不设线）：设置后排行行显示"达标"标签，未达标显示"距达标 X 学时"，卡片显示"达标 M/N 人"，成员端显示本人"已达标 / 未达标(差 X)"。

报表支持**导出 CSV**：按当前页签（学时排行 / 认定明细）生成 CSV 文件写入应用沙箱并显示文件路径，同时可"复制内容"到剪贴板，粘贴进 Excel/WPS 即可。

管理员额外提供"重算学时"：以 `signup` 表中已通过的记录为唯一事实来源重建 `hours_total`，用于修复历史手工改库、异常中断造成的数据漂移；重算为事务操作，正常数据下结果与重算前一致。

### 5.6 发布活动

发布活动为管理员功能，包含"活动表单 + 本地草稿箱"两部分：

- 表单字段：活动名称（必填）、内容（多行文本）、地点、学时、人数上限（0 表示不限）、发布人；
- 时间选择：点击"开始时间 / 结束时间"卡片弹出滚轮选择器（日期 + 时间两级滚轮），不可手工输入，杜绝非法时间；系统自动校验"结束必须晚于开始""开始不得早于当前"，不合法时自动调整或拒绝；
- 保存草稿：表单校验通过后写入本地 SQLite 草稿箱，可在离线环境随时编辑；
- 保存并发布：先落草稿再同步服务器（MySQL 新增活动记录），发布成功后草稿标记"已发布"，不会重复发布；
- 草稿箱：每条未发布草稿可"载入表单""发布到服务器"或"删除"，发布以草稿自身内容为准；删除有二次确认（本地草稿无云端备份）；
- 草稿载入表单：点"载入表单"把草稿回填到上方表单，表单进入编辑态（提示"正在编辑草稿 #n"），再次保存是**更新该草稿**而不是新建一条；发布成功后自动退出编辑态；点"退出编辑 / 清空表单"可放弃；
- 已发布活动管理：页面底部列出全部已发布活动（**含已下线**），每条可"编辑""下线 / 恢复上线"，点击活动名进入详情；下线后误操作可自行恢复，无需改数据库。

> 说明：草稿保存不校验"开始时间必须晚于当前"（允许补录历史活动的草稿），点"保存并发布"时才校验并由服务端复核。

### 5.6.1 编辑活动

在"发布活动 → 已发布活动"或活动详情页点"编辑活动"进入编辑页：回填当前标题 / 内容 / 地点 / 时间 / 学时 / 人数上限后保存，调用 `/api/activity/update` 在原记录上更新。规则：

- 允许保留早于当前的开始时间（便于修正历史活动的文案），但结束时间必须晚于开始时间；
- 人数上限不得小于当前有效报名数（页面会提示"当前有效报名 N 人"），服务端同样校验并返回实际人数；
- 已产生的报名记录与已认定学时不受影响；活动处于已下线状态时仍可编辑。

### 5.7 审核中心

审核中心为管理员功能，筛选与分页都在服务端执行：可按"全部 / 待审核 / 已通过 / 已驳回"筛选、按**活动下拉**（含已下线活动）过滤、按**姓名 / 学号 / 活动名关键词**搜索，三项条件可叠加；列表 20 条/页，底部提供"上一页 / 下一页 · 第 P 页 · 共 N 条"。对待审核记录点击"通过"或"驳回"：**通过按钮会直接显示本次将认定的学时（取该活动学时，而非报名记录当前的 0）**，通过时服务器自动把该活动学时累计进该成员学时汇总（事务保证不重复累计）；驳回则记录状态与备注。交互细节：

- 通过/驳回均弹出确认对话框，防止误触（驳回后成员需重新报名，操作不可逆）；
- 已审核的记录在服务端层面禁止重复审核（返回"该记录已审核，不能重复操作"）；审核本身为"事务内锁报名行 + 条件更新（status=0）+ 影响行数校验"，即使两位管理员同时点通过（或网络重试）也只会累计一次学时；
- **列表过期不会静默失败**：若成员在管理员点"通过"之前撤销了报名，服务端返回"该报名已被学生撤销或不存在，请刷新列表"，页面同时弹出 toast 并在操作区显示红色错误提示（不再是一行灰字）；
- 审核结果在成员端"我的报名"同步后可见。

审核中心顶部有**"报名审核 / 注册申请"两个页签**。切到"注册申请"可看到自助注册的待审清单（学号、姓名、班级、注册时间），对每条点"同意"或"拒绝"：同意后该学生立即可登录，拒绝则保留记录但禁止登录。已加入的成员在"注册申请"里不再出现（只列待审/待处理项），其完整信息与注销入口统一在"用户管理"页。

### 5.8 服务器实时日志

服务器实时日志为管理员功能，默认每 3 秒自动刷新，展示最近若干条请求（时间精确到毫秒、方法、路径、状态码、耗时、来源 IP）。支持按"全部 / 失败 / 慢请求"与"ALL / GET / POST"两组条件筛选，并可输入路径关键词（如 `/api/signup`）过滤；慢请求（≥500ms）额外标"慢"。每次 App 请求服务器都会实时出现在此处，同时写入 MySQL 的 request_log 表，可直接用 SQL 查询核验。可切换手动刷新。

### 5.9 设置

设置页可修改服务器地址（IP + 端口），**无需登录即可访问**（引导页"设置"入口恒在）。保存时会校验：地址不能为空、不能带 `http://` 或空格，端口必须是 1~65535 的整数；点"测试连接"会先保存当前输入再探测，避免改完地址却测到旧地址。模拟器联调用 10.0.2.2:8000；真机演示需改为宿主机局域网 IPv4（如 10.15.85.109）并保证同一局域网、服务器已放行 8000 端口。页面提供"测试连接"按钮与当前账号信息、退出登录（退出时同时请求服务端注销 Token，避免旧 Token 在 24 小时有效期内继续可用）；连接失败时也可在此修改地址后重新测试。退出登录（含主界面"我的"页退出）会先请求服务端注销 Token，再**清空返回栈**回到引导页，不会停留在已失效的主界面；Token 过期或服务端重启导致的 401 会自动清除本地登录态并提示重新登录。

设置页还包含两处与演示直接相关的能力：

- **模拟刷卡（仅管理员）**：选择"未结束且未满"的活动后点"模拟刷卡"，走的是与 ESP32 完全相同的 `/api/signin` 接口（不是本地假数据），因此 ESP32 硬件不在场时也能完整演示"刷卡→签到→累计学时→双端可见"这条链路；
- **危险操作（仅普通成员）**：见 5.11 账号注销。

### 5.10 用户管理

入口：管理 Tab → "用户管理"（第二位卡片）。这是管理员的**全量学生视图**，与审核中心的分工是：审核中心处理"待办的事"，用户管理查看"全部的人"。

- 顶部：返回、标题"用户管理"、"共 N 人"（随筛选结果变化）与刷新按钮；
- **分组查找**：六个分组标签以 2 行 3 列排布（避免横向滚动被裁切），分别是"全部 / 待审核 / 已通过 / 已驳回 / 已达标 / 未达标"，每个标签带实时人数。分组在**服务端**过滤（不是先拉全量再前端筛），因此 `total` 与列表行数始终一致，不会出现"翻页少人"；
- **关键词搜索**：支持学号、姓名、班级，与分组条件叠加生效（如"未达标 + 计科"）；
- **学生卡片**：姓名、注册状态徽标（待审核/已通过/已驳回，颜色区分）、学号·班级、右侧学时摘要与达标进度条（未设达标线时显示"未设置"）、RFID 卡号（未绑卡显示"未绑卡"）、注册日期（只到日）；
- **注销入口**：每张卡片右下角"注销"，点开在当前卡片下**内联展开**确认面板（同一时刻只展开一个，避免误点多个），面板如实列出"将删除报名 M 条、学时 X"，并要求输入该生学号后才可点"确认注销"。详见 5.11。

> 排序规则：待审核优先（管理员需要先处理它们），其余按学时降序，因此"谁学时最高"在列表里一眼可见。

### 5.11 账号注销

系统提供两条注销通道，**都是不可逆的硬删除**（不是标记删除、不是隐藏）：

| 通道 | 入口 | 操作人 | 可注销对象 |
|---|---|---|---|
| 学生自助注销 | 我的 → 设置 → 危险操作 → 注销账号 | 本人 | 仅本人 |
| 管理员注销 | 用户管理 → 卡片"注销" | 管理员 | 任意学生 |

**操作流程（两步，先看清再动手）**

1. 点注销后先向服务端查询**影响面**（`GET /api/student/impact`），页面如实展示：报名总条数、其中已通过/待审核/已驳回各几条、已认定学时合计、注册状态。学生端需先点"注销账号"才展开，管理员端在卡片内联展开；
2. 输入**被注销人的学号**（学生填本人学号，管理员填该生学号）才激活"确认注销"按钮。学号不匹配时按钮保持禁用，服务端也会二次校验（前端比较 + 服务端校验双保险，绕过 UI 直接打接口同样会被拒）。

**注销后数据如何处理（这是本功能的重点）**

服务端在一个事务内按 `signup → hours_total → student` 顺序级联删除，任一步失败整体回滚，不会留下半条数据：

- **报名记录**：该生全部报名（含已通过、待审核、已驳回）一并删除，活动名额随之释放；
- **学时汇总**：`hours_total` 中该生的汇总行删除，排行榜与报表立即不再出现该生（排行榜是动态查询，不做缓存）；
- **账号本体**：`student` 行删除，其学号可从"用户管理"和登录入口彻底消失；
- **登录态**：该学号名下所有 Token 立即回收，其他设备上仍在登录的会话下次请求会收到"登录已失效"并自动清除本地登录态（不会出现"看着已登录、点什么都没反应"）；
- **本地缓存**：App 端同时清掉本地 `local_signup` 中该学号的历史报名缓存，避免注销后本地还显示旧记录；
- **审计日志保留**：`request_log` 表**不删**（无外键关联），注销动作本身以 `AUDIT` 标记留痕，便于事后追查"谁在什么时候注销了谁"；
- **RFID 卡号自动解绑**：刷卡逻辑按卡号反查学生，学生行删除后该卡自然失效（返回"卡号未绑定任何成员"），卡片可重新绑定给新账号；
- **学号可复用**：注销是物理删除，同一学号可以重新注册（重新走注册审批流程），不会与历史数据冲突。

**并发安全**：注销时对 `student` 行加 `FOR UPDATE` 行锁，实测 4 路请求同时注销同一账号，恰好 1 个成功、其余返回"该学号不存在或已注销"，三张表零残留。

**演示建议**：先演示"学时报表双端一致"（20.5 学时基线），再演示注销。注销后学时总额会下降（被注销人的学时被真实移除），这是设计如此而非数据错误——如担心评审误解，可先说明"接下来演示注销，总额会同步减少"。

### 5.12 错误提示与失败反馈

系统的原则是**不存在静默失败**：任何写操作（报名、撤销、审核、发布、编辑、注销、设置达标线…）只要没达到预期结果，都会给出可读的中文原因。

- **全局 toast**：所有 POST 操作失败自动弹出 3 秒 toast（底部浮动），批量操作（如"全部通过"）内部调用传静默参数，只汇总统计不逐条刷屏；
- **服务端消息中文化**：业务错误消息全部为中文，例如"该报名已被学生撤销或不存在, 请刷新列表""名额已满, 无法报名""活动未开放报名""活动不存在或已下线""该学生不存在或已注销""数据库连接失败, 请检查 MySQL 服务"；
- **页面级红字**：审核中心等页面的操作结果区在失败时染红加粗并允许两行，与成功提示在视觉上区分；
- **登录失效自动兜底**：服务端约定"业务错误也走 HTTP 200，错误码在响应体"，App 端因此同时检查 `HTTP 401` 与响应体 `code==401`，命中即清除本地登录态并提示重新登录（这是历史上一处真实缺陷，已修）。

**典型场景**：成员报名后管理员未刷新列表，成员在此期间撤销报名，管理员再点"通过"——页面会弹出"该报名已被学生撤销或不存在，请刷新列表"，而不是无反应；同时学生学时、活动名额都不受影响。

## 7 嵌入式扩展项：ESP32 + RFID 刷卡签到

ESP32 通过 SPI 连接 MFRC522 读卡模块，刷卡后把卡号上报服务器，服务器按卡号匹配学生并完成签到与学时认定。此扩展项可脱离 App 独立演示，与 Web 端数据互通。

### 7.1 硬件接线

| MFRC522 引脚 | ESP32 引脚 |
|---|---|
| SDA (SS) | GPIO5 |
| SCK | GPIO18 |
| MOSI | GPIO23 |
| MISO | GPIO19 |
| RST | GPIO27 |
| 3.3V | 3.3V |
| GND | GND |

### 7.2 配置修改

修改 esp32_rfid\rfid_esp32.ino 顶部的配置区：WiFi 名称与密码、服务器地址（SERVER_BASE，填宿主机局域网 IPv4:8000）、要签到的活动 ID（ACTIVITY_ID，需为已发布且未结束的活动）。编译烧录后打开串口监视器，即可看到刷卡上报结果。固件已做两处现场保护：WiFi 掉线每 5 秒自动重连（无需重启设备）、同一张卡 5 秒内不重复上报（卡一直放在读头上也不会刷屏）。

若希望限制"只有本终端能刷卡"，可给服务器加设备密钥：启动时追加第 5 个参数或设置环境变量 `CLUB_DEVICE_KEY`，例如 `server.exe 8000 root 123456 127.0.0.1 club-rfid-2026`，同时把固件里的 `DEVICE_KEY` 改成相同值；此后未带正确 `X-Device-Key` 头的刷卡请求会被拒绝（返回 401）。不配置则保持原行为（不校验）。

### 7.3 签到认定逻辑

服务器对刷卡请求按卡号匹配学生后：若该活动无报名则自动创建并通过（到场认定）；若报名待审核则置为通过并认定学时；若已通过则仅标记签到；若报名已被管理员驳回则拒绝签到（提示需先重新报名），避免刷卡绕过人工审核；活动已下线或已结束则拒绝认定。学时累计为事务操作，且"待审核→通过"的更新带 `status=0` 条件与影响行数校验，重复刷卡、并发刷卡都不会重复累计。**注意：如果活动中没有报名记录，刷卡会自动建一条已通过记录，因此演示"刷卡签到"时应先确认该活动的报名情况，或在演示前说明这一"到场认定"设计。**

## 8 常见问题（FAQ）

| 问题 | 原因与解决办法 |
|---|---|
| App 提示"无法连接服务器 / Operation timeout" | 检查服务器是否已启动且监听 0.0.0.0:8000；App 设置页服务器地址是否为 10.0.2.2（模拟器）或宿主机局域网 IPv4（真机）；Windows 防火墙是否放行 8000 端口 |
| 真机连不上服务器 | 手机与电脑需在同一局域网；服务器地址填电脑的局域网 IPv4（可在设置页查询）；服务器需 bind 0.0.0.0 |
| 登录提示"未登录或登录已过期" | 服务器重启后内存 Token 失效，退出重新登录即可 |
| 活动时间无法输入 | 发布时间采用滚轮选择器，仅能滚动选择并自动校验"结束晚于开始、开始不早于当前"，无法手工输入非法时间 |
| 重复报名会重复吗 | 不会。本地按 client_id 幂等、服务器按唯一键去重，重复点击只保留一条记录 |
| 审核通过后学时没变 | 学时累计在服务器事务内完成，刷新"学时报表"查看；成员端点击"我的报名→同步服务器状态"刷新本地 |
| 刷卡提示"该报名已被管理员驳回" | 驳回是管理员的人工决策，刷卡不会绕过审核；成员需在活动详情页点击"重新报名"，管理员通过后再刷卡签到 |
| 刷卡提示"活动已结束, 不能再刷卡认定学时" | 活动结束时间已过，出于数据可信性不再接受签到；如需补录请由管理员调整活动时间或直接审核报名 |
| 报名成功后提示"仅本地(未同步)" | 服务器当时不可达（地址错误/未启动）。修正服务器地址后，在"我的报名"点"立即补传"或重新进入页面，会自动补传；服务端按 client_id 幂等，不会重复报名 |
| 提示"登录失败次数过多, 请 60 秒后再试" | 同一账号 60 秒内连续输错 5 次会临时锁定（防暴力猜测），等待 60 秒或重启服务端即可恢复 |
| 学时汇总与实际认定不一致 | 管理员进入"学时报表"点"重算学时"，服务器会以已通过的报名记录重建 hours_total |
| 运行 test_api.py 会不会清掉演示数据 | 默认不会（保留现有数据）；只有显式加 `--reset` 参数才会把 signup 重置为待审核并清空 hours_total |
| 历史版本"审核中心闪退" | 已修复：页面状态改为显式过滤渲染，不依赖列表下标直接索引；当前版本可稳定使用 |
| MySQL 数据如何查验 | 连接 club_system 库查询 activity / signup / hours_total / request_log 各表即可；验收演示建议展示 hours_total 与 request_log |
| 注销后同一学号还能再注册吗 | 能。注销是物理删除（报名、学时、账号本体一并清除），学号可重新走注册审批流程 |
| 注销后学时总额变少了，是数据错了吗 | 不是。注销会真实删除该生的学时记录，总额同步下降；排行榜与报表均为动态查询，无残留 |
| 管理员点"通过"提示"该报名已被学生撤销或不存在" | 列表是点击前的快照，成员在此期间撤销了报名。点刷新即可，学时与名额均未受影响 |
| 导出的 CSV 用 Excel 打开中文乱码 | 导出时已写入 UTF-8 BOM，正常双击不应乱码；若仍异常，请用 Excel"数据 → 从文本/CSV"导入并选择 UTF-8 |
| 关掉服务端窗口后 App 提示登录失效 | 服务端 Token 存于内存，重启即清空。重新登录即可；演示期间请不要关闭该窗口 |
| 演示前怎么确认数据没被测试脚本改坏 | 在 server 目录执行 `python verify_demo_data.py`，应输出 8 活动 / 19 报名 / 5 人 / 20.5 学时；详见第 9 节 |
| 真机 `hdc install` 报签名错误 | 当前产物是 unsigned HAP，只能装模拟器；真机需在 DevEco 配置自动签名后重新构建（见 3.3） |
| 服务端启动窗口一闪就没了 | 说明 MySQL 未启动或 exe 被占用；`start_server.bat` 会先检测 3306 并停住显示原因，按提示启动 MySQL 服务即可 |
